## 28/7/2026

Found and fixed a scoring bug affecting every notebook: ViNumQA gold programs use `table_sum/table_average/table_max/table_min(row_name, none)`, where the first argument is a table row _name_ to look up — not a list of numeric values, as every notebook's SYSTEM*MESSAGE incorrectly described and every hand-rolled evaluator assumed. This silently scored EA=0 on any sample using a table*\* op (~12% of test.json) and, more importantly, meant every 0/1/few-shot prompted model was being taught the wrong output format directly in the prompt. Applied the fix (corrected SYSTEM_MESSAGE, added a table_raw column so the evaluator can see the real table, swapped in scorer.py) across all 0-shot/1-shot/few-shot notebooks and both SFT notebooks. Added the two missing 1-shot notebooks (FPT API and Qwen3-4B/Kaggle) to match the existing 0-shot/few-shot coverage.

## 5-6/8/2026

Designed and ran the first pass of **STaNR (Self-Taught Numerical Reasoning)**, our proposed method: after ordinary SFT with a teacher-distilled reasoning-trace set (SFT w ENG trace, PA-match-only), use that fine-tuned checkpoint itself as a second-round teacher on the samples the _original_ teacher (gemma-4-31B-it) failed to solve during independent-solve distillation, keep only the self-generated traces whose program matches gold under PA, and merge them into the training set for one more SFT pass. Ran this for Qwen3-4B: `train.json` minus `train_with_reasoning_trace_en_pa_distiil_gemma.json` (matched by `id`) gave 870 teacher-failed train samples (plus a matching valid-side count); dual-GPU self-distillation on the fine-tuned checkpoint recovered 117/870 train and 26/~183 valid samples that passed the PA filter, producing `STaNR_en_v1_qwen3-4b_self_train.json` / `_valid.json` (2,240 / 476 total samples, `qa.trace_source` marking `independent` vs `self_distilled`).

Manually read all 26 self-distilled validation samples end-to-end (not just automated leak/length checks) before trusting the method: 0/117 train and 0/26 valid samples matched an expanded leak-phrase denylist, trace length/step-complexity were in normal range, but two concrete quality problems surfaced on close reading — one sample's trace visibly hedges and self-corrects mid-reasoning before landing on the (correct) `table_max` call by coincidence rather than understanding why it applies, and a second sample fabricates a nonsensical "cost of goods sold = revenue − pre-tax income" formula to match a gold label that is itself likely mislabeled upstream. Concluded the PA-match filter alone doesn't catch "right answer via unsound reasoning," at an estimated 3-5% rate in the self-distilled subset — a data-quality caveat to carry into interpreting STaNR results, not a blocker.

First scored run of the resulting Qwen3-4B checkpoint on `test.json` looked like a severe regression (PA 0.352 / EA 0.372, well below every other configuration), which didn't match the manual-review finding of mostly-sound self-distilled data. Traced this to an evaluation bug, not a modeling one: 192/497 (38.6%) of the checkpoint's outputs failed to parse as a program at all, because the `</think>` token-boundary split (used to separate the reasoning trace from the program in the raw generation) was landing in the wrong place on this checkpoint often enough to leak reasoning prose into the `generated_program` column. Instrumented the dual-GPU eval notebook (`qwen3-4b-eval-only-dual-gpu.ipynb`) to save the full raw decode (`skip_special_tokens=False`) and a `found_think_close` flag per sample alongside the parsed halves, and added a manual-review cell that prints every sample where `</think>` wasn't found first. Root-caused and fixed the underlying split logic, re-ran: 0/497 samples now fail the `</think>` split, and the corrected score is **PA 0.6680 / EA 0.7163** — above the PA-match-only baseline (0.6519/0.6962) it was built from, and above the cross-model STaNR_v1 variant (self-distilled from qwen3-4b-thinking instead of from itself, 0.6559/0.7123). This reverses the working hypothesis from the previous session (that self-distilling a model from its own checkpoint amplifies its own bias and hurts performance, based on qwen3-4b-thinking's STaNR_v1 number looking worse than baseline at the time) — the regression there also turned out to trace back to how the self-distilled samples were selected, not an inherent self-loop problem: teammate Chi re-ran qwen3-4b-thinking's self-distillation with k=5 sampling per teacher-failed sample (keep the program that's the modal answer across 5 independent generations, first-generation as tiebreak) instead of a single generation, and qwen3-4b-thinking's STaNR_v1 number rose from PA 0.6579/EA 0.7203 to **PA 0.6801/EA 0.7404** — now clearly above its own PA-match-only baseline (0.6660/0.7223) too. ## 11/8/2026

Designed the GRPO reward function for ViNumQA, following the PCPO paper's (Chu et al. 2025) program-centric framing rather than a generic answer-match reward: a single tiered `compute_reward` — PA=1.0 (program symbolically matches gold, via `scorer.py`'s existing `equal_program`) > EA-only=0.3 (executes to the right number but isn't the same program — reuses gold's operator sequence by coincidence or a different valid derivation) > invalid/wrong=0.0 — plus a capped conciseness penalty (0.05 per step over gold's step count, capped at 15% of the base reward) so GRPO can't farm reward by padding programs with no-op-equivalent extra steps. Chose PA as the top tier over EA because PA is the stricter, more meaningful signal for this task (symbolic derivation match, not just a lucky correct number), and gated the conciseness penalty's cap so it can never flip a correct-but-verbose program's reward below an incorrect one's.

Before committing this reward to a real GRPO run, built a **sanity-check pass** ("Part A") on the existing SFT checkpoint (`SFT w ENG trace; PA-match-only`, Qwen3-4B): sample 20 test questions, generate G=8 completions each at `temperature=1.0` (matching the GRPO training config, not greedy — collapsed groups give zero learning signal), score all 160 completions, and inspect the distribution of per-group reward variance. Zero-variance groups (`std=0`) contribute nothing to GRPO's within-group relative advantage, so a large fraction of them would mean the checkpoint is already too saturated (or too uniformly wrong) for this reward to teach anything on this data. Result: enough non-zero-variance groups to proceed, so no reward redesign was needed before training.

Loading the model for both the sanity-check and the actual GRPO training pass required solving a smaller but important problem first: **continuing GRPO on the existing SFT LoRA adapter**, not training a fresh one from the base model (unlike Unsloth's own GRPO template, which pre-fine-tunes the base model from scratch). Since `fast_inference=True` (vLLM) can't point `model_name` directly at a LoRA adapter directory — vLLM always loads the base model first — the pattern settled on was: read `base_model_name_or_path`/`r`/`lora_alpha`/`target_modules` out of the adapter's own `adapter_config.json` (source of truth, not a hardcoded guess matching the checkpoint), load that base model, recreate the identical LoRA structure via `get_peft_model()`, then load the trained weights into that structure with `set_peft_model_state_dict()`. This makes GRPO continue optimizing the actual SFT-trained weights rather than starting a new adapter from random init.

Iterated through GPU sizing for this setup. First attempt was a single Kaggle T4 (14.5GB), which OOMed at `trainer.train()`'s first step once `GRPOConfig`'s `per_device_eval_batch_size` was raised to satisfy the "must be a multiple of `num_generations`" constraint (needed for an `eval_dataset` to work at all) — the eval batch's own G=8 completions on top of the train batch, vLLM's standby-mode shared VRAM, and the reference-policy KL forward pass didn't fit together. This closes all three error classes at the image level instead of three separate environment-variable workarounds, and matches how Kaggle avoids them by starting from a devel-class image in the first place.

With the environment fixed, ran GRPO training and made three further design decisions based on what the training curves showed:

- **In-training eval + early stopping.** The Kaggle/T4 notebook had `eval_strategy="no"` (an eval pass's own G=8 completions per prompt didn't fit alongside the train batch on 14.5GB). On the A100-80GB this is affordable, so wired up `eval_dataset` and `EarlyStoppingCallback`, but keyed `metric_for_best_model` on **`eval_reward`**, not `eval_loss` (the SFT notebooks' pattern) — GRPO's loss is a policy-gradient surrogate that doesn't track answer quality, whereas `eval_reward` is the same PA/EA-tiered reward function averaged over the validation set, making it a near-direct proxy for validation PA without needing a separate `compute_metrics` pass.
- **Fixed eval cadence instead of computed.** Initially derived `eval_steps` from `steps_per_epoch // 10`, but real timing showed each eval pass over the full ~450-sample validation set takes ~37 minutes (450 prompts × `num_generations=8` completions each — the group-sampling requirement that makes GRPO eval inherently ~8x more expensive than a plain PA/EA pass), and one epoch runs ~530 optimizer steps at ~0.03 it/s. Fixing `eval_steps=100` (and matching `save_steps=100`, required for `load_best_model_at_end`) gives 5 evals across the epoch (~3 hours of eval time total) — a deliberate choice to keep total eval cost bounded on a rented A100 rather than auto-scaling eval frequency to dataset size. Lowered `EarlyStoppingCallback`'s patience from 3 to 2 to match — with only ~5 eval points in a single epoch, patience 3 would rarely have room to trigger before the epoch just ends on its own.
- **One epoch, no `max_steps`.** Switched `GRPOConfig` from a fixed `max_steps=100` (Kaggle) to `num_train_epochs=1`, on the reasoning that the reward-tier design and PA baseline of the starting checkpoint (already ~90% train reward in early Kaggle runs) leaves a narrow ceiling for GRPO to improve within — early stopping is the safety net against over-training into reward-hacking territory (observed one single-step KL spike to 3.2 on Kaggle that self-corrected by the next step, not a sustained drift, but the kind of transient the early-stopping checkpoint selection is meant to catch if it doesn't self-correct next time).

Confirmed via TRL v0.22.2 source (fetched `trl/trainer/grpo_trainer.py` directly, not guessed) that `metric_for_best_model="eval_reward"` was wrong on a different axis than expected: GRPOTrainer _does_ compute and log reward during eval (visible in console/wandb, under `eval_rewards/{reward_func_name}/mean`), but `GRPOTrainer.log()` rebinds a local `logs` dict rather than mutating the one `Trainer.evaluate()` returns — so the reward key never reaches the `metrics` dict that `metric_for_best_model`/`load_best_model_at_end` actually check, which only ever sees `eval_loss`. This is a known, currently-open TRL gap (issue #2959, fix in unmerged PR #5790), not something fixable by trying a different key name — spent two guessed key names (`eval_reward`, then `eval_rewards/program_reward_func/mean`) before pausing to verify against source instead of guessing a third, since each guess costs a real Modal GPU run to hit the `KeyError`. Replaced `load_best_model_at_end`/`EarlyStoppingCallback` entirely with a hand-rolled `RewardBestCheckpointCallback` that reads the reward value out of `state.log_history` instead (which _does_ get the key, via `super().log()`'s append, independent of the dict-merge gap above) — tracks best-reward-so-far, saves that adapter directly, and sets `control.should_training_stop` after `patience` evals without improvement.
